### The router hold finding: confirmed

`README.md:92-94` records this builder finding. It holds at `32d73ef`, and I re-read every line
cited here:

1. `lib/imaging/router.ts:311` reserves **one** hold per request.
2. Inside `walk(currentHold)`, a candidate that throws a billed error reaches `:428-439`, which
   calls `settle(currentHold, {outcome:"failed", basis:"estimate"})`. `settle` deletes the hold
   and books the row (`lib/spend/meter.ts:265-268`).
3. If the error is reroutable (`:443`), the loop moves on to the next vendor **with the
   already-deleted hold id**. Nothing new is reserved, so the second vendor is called with no
   ceiling check.
4. If that vendor serves, the success path settles the dead id (a no-op delete) and books the
   served row anyway (`:383`). The `finally release(hold)` (`:327`) is a no-op too.
5. Net effect: one request can book the failed estimate **plus** the served cost after reserving
   one estimate. While the second call is in flight, `held` does not include it, so concurrent
   requests are not held back either.

**Reach.** The only kind that is both billed (`billedOnFailure`, `router.ts:251-267`) and
reroutable (`lib/imaging/errors.ts:107-109`) is `refused`. Production chains have one entry each
(`router.ts:103-107`), so the bug can only fire on the dev chains: generate `agy → google →
leonardo` (`:88`) and recognize `ollama → google` (`:101`).

**Fix shape.** Keep the request-level reserve at `:311`. Three probes depend on it:
