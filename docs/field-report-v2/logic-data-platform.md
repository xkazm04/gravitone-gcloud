## 0. Orientation + independence declaration

**Stack:** Next.js 16 / React 19 / TS 5, Tailwind 4, Firebase Auth (Google-only), **no server DB** — persistence is browser IndexedDB (`lib/studioDb.ts`) + a localStorage seed flag. Four runtime deps total. Server surface is thin: six Next.js route handlers under `app/api/` (`imaging/{generate,edit,recognize,pricing}`, `frames`, `recalibrate`). The AI surface is real and central: a vendor-agnostic imaging chokepoint routing Google (Nano Banana 2) / Leonardo / Qwen, plus two headless **local `claude` CLI** calls (`lib/claudeCli.ts`) for art-direction (`/api/frames`) and edit-plan generation (`/api/recalibrate`).

**Entanglement with the corpus — material, and it cuts two ways:**
1. `.claude/patterns/README.md` is *"Auto-generated by personas workspace_projection (pattern-fabric F2)"* — this repo receives **284 adopted Personas engineering patterns** as standing guidance. `CLAUDE.md`'s context-map block is generated by the Personas app. So the repo is a **downstream of Personas' conventions**, not a stranger to them.
2. Several files name the Personas reference explicitly and say they *improved on it*: `lib/imaging/json.ts` ("the reference implementation in the personas repo asks for JSON in the prompt and then prints whatever comes back — validation is left to nobody"), `lib/imaging/providers/leonardo.ts` (constants "taken from a WORKING client in the reference repo … not from documentation"), `qwen.ts` ("Two improvements over that reference client, deliberately").

**Consequence for scoring:** none of these leaves is `holds(self)` — the corpus docs live in `personas/` and were authored from `personas/`, not from gravitone. But a hold here is **not blind convergence**; it is a deliberate, informed re-implementation in a different stack by an author who knows the reference. That is still strong evidence the *physics generalizes across stacks* (it survives the Rust→browser port and the author chose to keep it), but weaker than an independent team arriving at the same shape unaware. Flagged per-leaf where it matters.

## 2. Deviations (nothing applied) — worth a fix

**D1 — `/api/imaging/*` routes are unauthenticated; each one spends real money. (severity: MEDIUM; held: single-operator prototype)**
`grep` for `auth|verifyIdToken|session|uid` across `app/api/` returns **no server-side auth** on any route. The Firebase gate is client-side only (gated routes bounce to `/`); a server handler has no gate. `generate`/`edit`/`recognize` each bill a live vendor balance, and `frames`/`recalibrate` each spawn an Opus-5-at-high-effort local run. Anyone who can reach the origin can drain the balance and there is **no spend-ceiling** (`spend-ceilings` = n/a-absent) to bound the damage. *Held because:* `.env.example` frames this as a single-operator local/self-hosted tool, keys are optional, and the app is pre-release. *Fix when it deploys multi-user:* an ID-token check in a shared route helper + a per-window spend ceiling (`headless-model-call`'s owner/payer clauses, currently `n/a-scope`, become real the moment a second user exists).

**D2 — no SSRF-safe client on the vendor-supplied download URL. (severity: LOW-MEDIUM; held: URL comes from a trusted vendor API, not a user)**
`lib/imaging/http.ts:537` `fetchImageBase64` fetches a URL returned in Leonardo's poll response. It is bounded by size (32MB, with a content-length pre-check) and timeout — good — but not by host: nothing stops the far end being an internal address. The corpus `outbound-http-call` physics asks "can anything a user or a config supply influence the host? if yes → SSRF-safe client." Here the host is **vendor-influenced** (one hop of trust from Leonardo's API). *Held because:* the URL originates from an authenticated vendor response, not user input, and the app is single-user. *Fix:* front the download with a host-allowlisted / private-range-blocking client if this ever runs where the Leonardo account is not fully trusted.

**D3 — `next.config.ts` sets no CSP / security headers. (severity: LOW; held: prototype)**
`tauri-permissions-and-csp`'s web analogue. The app renders model-composed content and base64 plates; a `Content-Security-Policy` and the usual headers (`X-Content-Type-Options`, `Referrer-Policy`) are the cheap floor. Absent. *Fix:* a `headers()` block in `next.config.ts` before public deploy.

## 4. Methodics

- **Executed vs shallow.** Executed checks: `grep` for auth in `app/api/` (0 hits → D1), `grep` for spend/rate-limit/ceiling across `lib`+`app` (0 real hits → `spend-ceilings` n/a-absent), `grep` of `projectSeed.ts` ids (confirmed content-named seed ids underpinning the CAS reasoning). ~28 files read in full for breadth. True multi-angle dives (~8): SSRF host-trust (traced the Leonardo URL from poll response → `fetchImageBase64`), pricing single-source (route header audit cross-checked against `PRICES` + `estimatePerImage`), scrub ordering (verified `liveSecrets()` runs before the regex passes), IDB `tx.error`-null claim (read the capture-phase workaround), seed-race CAS (`add` vs `put` + `ConstraintError` swallow in `addProjects`).
- **No two-implementation disagreements** of the kind the kit warns about — but one **count caveat**: clause counts per leaf are my read of the stack-free head from `index.json`'s `oneWay` field (the head prose, not the full doc); I did not open all 90 corpus `.md` bodies, so a leaf's true clause enumeration (P1/P2/…) may differ from my "~N". Flagged per row with `~`.
- **Self-correction.** Initially inclined to score `outbound-http-call` a `holds` on the strength of the size/timeout bounds; corrected to `partial` after confirming the host itself is unbounded and vendor-influenced — the corpus physics is about *host* control, which the size ceiling doesn't address.
- **Instrument gaps.** No test framework in-repo (by design — `integration-imaging.mts:8`), so I could not *run* the gates to observe pass/fail; I read them statically and trust their self-described OK/FAIL/exit contract. I did **not** run any build/`next`/`tsx` command (kit rule). The Personas app bridge (for a live context-map read) was not probed — out of shard scope.
- **Independence honesty.** The strongest holds (redaction, accounting, typed errors, structured extraction) are *informed* re-implementations of a named Personas reference, not blind convergence — I have not inflated them to `holds(self)` (the corpus isn't authored here) but I've marked them "non-blind" so the aggregator doesn't read cross-stack agreement as independent discovery.
