## Keeping the context map true — the gate, not the reflex

Everything above the markers and everything below them is hand-written and safe to edit. The block
between the markers, and `context-map.json` itself, are **generated by the Personas app** from its own
database. There is no import path: **a hand edit to `context-map.json` is erased by the next scan**,
and until then it is a lie that six skills (`/architect`, `/explorer`, `/perfect`, `/scan-sweep`,
`/spark`, `/uat`) read as truth. So never edit it — refresh it instead, in the session that caused the
drift.

This repo is young and about to grow a lot: each studio step (script · frames · motion · score · cut)
becomes its own body of code. A map that lags behind that growth is worse than no map, because the
contexts stop matching where the work actually is.

### When to refresh — ONE question, and it is not "did I add a file"

This section used to say: *refresh if your session added, moved, renamed or deleted any file under
`app/` or `components/`.* That is an obligation, not a gate, and it fires on almost every session.
Measured 2026-08-29: three commits from three different sessions each added a file under `app/` in one
morning, so all three were "required" to scan, none could see that another already had, and the map
took two scans in forty-four minutes. A scan is minutes of a real model run — the cost is the
operator's, and a delta scan over a map that was already right can only churn it.

So the trigger is a MEASUREMENT, and it is free:

Save it as `map-gate.py` or paste it; it needs no arguments and touches nothing.

```python
import json, os, subprocess, collections
CODE = {".ts", ".tsx", ".mjs", ".mts", ".py", ".css"}
d = json.load(open("context-map.json", encoding="utf-8"))
mapped = {p for c in d["contexts"] for p in c["file_paths"]}
dirs = {p.split("/")[0] for p in mapped if "/" in p}
tracked = subprocess.run(["git", "ls-files"], capture_output=True, text=True).stdout.split()
src = [p for p in tracked if p.split("/")[0] in dirs and os.path.splitext(p)[1] in CODE]

# WHEN THE MAP LAST SPOKE. Everything added after this commit is a file the map
# has never been offered, so it must not be allowed to vote on whether the
# directory that holds it is well covered.
#
# THIS LINE IS THE WHOLE FIX. The band used to be computed over every file
# present now, which means a big enough batch of new files DILUTES its own
# directory past the 0.9 threshold, flips it from `comprehensive` to
# `selective`, and gets itself reported as "a choice, not drift". Measured
# 2026-09-08: components/ was 18/18, twelve files landed, it read 18/30 = 60%,
# and the gate filed twelve genuinely-missing files under the heading that means
# nobody has decided about them. The bigger the drift, the more invisible it was.
mapT = int(subprocess.run(["git", "log", "-1", "--format=%ct", "--", "context-map.json"],
                          capture_output=True, text=True).stdout.strip() or 0)
added = {}
cur = 0
for line in subprocess.run(["git", "log", "--diff-filter=A", "--format=@%ct", "--name-only"],
                           capture_output=True, text=True, errors="replace").stdout.splitlines():
    if line.startswith("@"):
        cur = int(line[1:])
    elif line.strip():
        added.setdefault(line.strip(), cur)   # first seen == newest add, log is newest-first
# A file with no recorded add (untracked-then-tracked oddities) is treated as
# OLD, so it counts toward the band. Erring that way keeps a directory honest:
# an unknown file can lower coverage, never inflate it.
known = [p for p in src if added.get(p, 0) <= mapT]

per = collections.defaultdict(lambda: [0, 0])
for p in known:
    per[p.split("/")[0]][1] += 1
    per[p.split("/")[0]][0] += p in mapped
deep = {k for k, (m, t) in per.items() if t and m / t >= 0.9}

drift = sorted(p for p in src if p not in mapped and p.split("/")[0] in deep)
loose = sorted(p for p in src if p not in mapped and p.split("/")[0] not in deep)
stale = sorted(p for p in mapped if not os.path.exists(p))
fresh = sorted(p for p in src if added.get(p, 0) > mapT)

for k in sorted(set(p.split("/")[0] for p in src)):
    m, t = per[k]
    new = sum(1 for p in fresh if p.split("/")[0] == k)
    band = "comprehensive" if k in deep else "selective"
    pct = f"{m/t*100:5.1f}%" if t else "  n/a "
    print(f"  {k:12s} {m:4d}/{t:<4d} {pct}  ({band}){f'  +{new} since the map' if new else ''}")
print("DRIFT (scan)   :", drift or "none")
print("stale (scan)   :", stale or "none")
print("selective      :", f"{len(loose)} unmapped under {sorted(set(p.split('/')[0] for p in loose))}")
print("contexts:", len(d["contexts"]), "ungrouped:", len([c for c in d["contexts"] if not c.get("group")]))
```

THE BAND IS COMPUTED OVER THE FILES THE MAP HAS SEEN, not over every file present now, and that one
line is a fix for a hole big enough to hide the drift it was built to find. The band used to divide by
the live file count — so a batch of new files DILUTES its own directory past the 0.9 threshold, flips
it from `comprehensive` to `selective`, and gets itself filed under "a choice, not drift". The bigger
the drift, the more invisible it was. Measured 2026-09-08: twelve files landed in `components/`, which
was 18/18; it read 18/30 = 60% and reported all twelve as somebody's deliberate choice. Worse, the
same run showed `tests/` had already slipped to 89.6% — four tenths of a percent under the line — and
was silently swallowing eight files including `tests/live/_control.ts`, which the 2026-09-06 ledger
line had explicitly recorded as drift before the band flipped and erased it. Correcting the denominator
took DRIFT from 5 files to 25. Files newer than the map are now counted and named separately
(`+N since the map`), because a file the map has never been offered should not get a vote on whether
the map covers its neighbours.

- **DRIFT and stale both empty → DO NOT SCAN.** Say so in your report: `map: current (N contexts,
  0 drift)`. A new file inside a directory an existing context already owns needs no scan — the map
  tracks file OWNERSHIP, and a delta pass over it changes nothing but the timestamps. This is the
  common case, and the `selective` line is not a reason to scan.
- **DRIFT non-empty** → a **delta** scan. A file the map does not have, in a directory the map
  otherwise covers completely, is the map falling behind. This is the ordinary refresh.
- **DRIFT non-empty under a NEW directory with ~8+ source files** → a **subtree** scan of that
  directory (see the granularity rule at the bottom — a subtree scan of a thin directory will merge,
  not split, and may duplicate).
- **`stale` non-empty** → a delta scan; files the map still claims are gone.
- **The `selective` count is a standing fact, not a trigger.** `pipeline/` and `tests/` are mapped
  in part on purpose — the map holds the probe lane's named seams and the pipeline's entry points,
  not every script beside them. Report the number so it stays visible; whether those files should be
  mapped is the operator's call and a scan will not make it for them.

THERE IS NO GLOB LIST ANY MORE, and that is the point. The first version of this gate globbed
`app/**` and `components/**`; widening it to `lib/**` immediately found `lib/devAuth.ts` — the
test-automation bypass `lib/localMode.ts` spends a paragraph distinguishing itself from — unmapped
since the map was created. Three later rounds found the same hole three more times: `pipeline/**`,
then `tests/**`, then `knowledge/**`. A glob that does not cover a directory reports it as perfectly
mapped, and a hand-written list of directories is a second copy of the map that drifts from it. So
the gate reads the map for its directories and `git ls-files` for its files, and cannot be wrong
about a directory again.

### Then check whether somebody already did it

`.claude/scan-history/context-map.jsonl` is the ledger, one line per scan, append-only:

```json
{"at":"<ISO>","mode":"delta|subtree|full","subtree":"<path or null>","scan_id":"<uuid>","contexts_before":13,"contexts_after":18,"ungrouped_after":12,"by":"<skill or 'manual'>","note":"<=80 chars"}
```

**Read it before you scan.** If a scan of the same mode and scope landed within the last few hours and
your `unmapped` list is empty, skip and name the line you deferred to. Parallel sessions are the norm
in this repo — this file is the only way they can see each other, and it is the same shape as
`.claude/scan-history/scan-sweep.jsonl`, which already does this job for sweeps. **Append your line as
soon as the scan reports done**, before you do anything else with the result: a killed session that
scanned and recorded nothing makes the next one scan again.

### And say what happened to the groups

Every scan, and the skip case too, ends with one line: `map: N contexts, M ungrouped`. Read `ungrouped`
straight from the file — do not trust the generated block above, which prints per-group counts and
never mentions contexts that belong to no group at all. Between 2026-08-11 and 2026-08-29 this repo
went from 6 to 18 contexts while the GROUPED count stayed at 6, and nothing said so: the scan ingest
resolved a context's `group_name` only against groups declared in that same scan's output, and a delta
scan never re-declares an existing group, so every context it wrote got a NULL group behind a
`[Created]` line that read like success. Fixed app-side on 2026-08-29 (the ingest now seeds its
name→id map from the database and mints a group rather than writing NULL), so a scan from a build
after that date should leave `ungrouped` at 0 or say which group it had to create. **Rows written
before the fix stay NULL until the context is re-scanned** — a context that never changes is never
re-emitted, so if `ungrouped` is stubbornly non-zero, name those contexts in your report and let the
operator decide between a re-scan and assigning them in Dev Tools → Context Ledger.

### How to refresh (the app must be running)

The Personas app exposes a loopback bridge, and **every `/dev-tools/*` call needs the local token** or
it answers `missing or invalid local token` and nothing else. The port is not fixed either. Both live
in the app's own handshake file, `~/.personas/local-http.json` (`{"pid":...,"port":17400,"token":"..."}`)
- read them from there rather than probing, and probe 17400..17410 only if that file is absent.

```bash
# 1. The bridge, from the app's own handshake file (port AND token live here)
PORT=$(python -c "import json,os;print(json.load(open(os.path.expanduser('~/.personas/local-http.json')))['port'])")
TOK=$(python -c "import json,os;print(json.load(open(os.path.expanduser('~/.personas/local-http.json')))['token'])")
AUTH=(-H "x-personas-local-token: $TOK")
# 2. This repo's project id (stable; confirm against /dev-tools/projects if unsure)
PID=91d8170c-2be4-45ac-b509-256bfa7726f1

# 3a. Files changed inside existing areas → DELTA scan (cheap; updates only what moved)
curl -s "${AUTH[@]}" -X POST "http://127.0.0.1:$PORT/dev-tools/scan-codebase" \
  -H 'content-type: application/json' \
  -d "{\"project_id\":\"$PID\",\"root_path\":\"C:/Users/mkdol/dolla/gravitone-gcloud\",\"delta_mode\":true}"

# 3b. A NEW step directory that deserves its own context → SUBTREE scan (scoped, safe:
#     a subtree scan never clears the rest of the map)
curl -s "${AUTH[@]}" -X POST "http://127.0.0.1:$PORT/dev-tools/scan-codebase" \
  -H 'content-type: application/json' \
  -d "{\"project_id\":\"$PID\",\"root_path\":\"C:/Users/mkdol/dolla/gravitone-gcloud\",\"subtree\":\"app/_phases/motion\"}"

# 4. Poll until status is done/failed — it streams progress lines
curl -s "${AUTH[@]}" "http://127.0.0.1:$PORT/dev-tools/scan-status/<scan_id>"

# 5. The scan re-exports context-map.json + this CLAUDE.md block itself. Only if you need a
#    re-export without a scan:
curl -s "${AUTH[@]}" -X POST "http://127.0.0.1:$PORT/dev-tools/export-context-map" \
  -H 'content-type: application/json' -d "{\"project_id\":\"$PID\"}"
```

**Then append your ledger line** (`.claude/scan-history/context-map.jsonl`, shape above) - the scan is
not finished until the next session can see that it happened.

A scan costs a real LLM run, so it is a once-per-session act at most, and usually not one at all - see
the gate above. Report in your final message which mode you ran, what the map gained or lost, and the
`ungrouped` count.

If you lose a `scan_id` (a `curl` inside a `while read` loop eats stdin and swallows its output),
recover it from `GET /dev-tools/scans/{project_id}` — never relaunch blindly, that scans the same
scope twice at full token cost.

### ALWAYS verify the map after a scan — a scan can corrupt it

Measured on 2026-08-11, running a subtree scan over a 1-file directory: the model correctly refused
to create an under-band context and re-emitted the sibling instead — but it emitted a *create*
(`context_map_context`) rather than an *update*, so the row was **inserted a second time**, with a
null group, while the self-heal pruned the moved paths out of the original. The map briefly held two
`production-phases` contexts, one of them ungrouped, with five files double-mapped. Every scan mode
can do this. So after any scan:

```bash
python -c "
import json,os
d=json.load(open('context-map.json',encoding='utf-8'))
names=[c['name'] for c in d['contexts']]
print('duplicates:', {n for n in names if names.count(n)>1})
print('ungrouped :', [c['name'] for c in d['contexts'] if not c['group']])
print('stale     :', [(c['name'],p) for c in d['contexts'] for p in c['file_paths'] if not os.path.exists(p)])"
```

Then run **the gate from the top of this section again** for the coverage half. It is not repeated
here on purpose: it used to be, with its own copy of the glob, and when that glob was widened this
copy was not — so the post-scan check inherited the blind spot the trigger had just lost. Two copies
of a rule are two rules. What a scan should move is the per-directory percentages and `DRIFT`; if a
scan leaves `DRIFT` non-empty, it did not map what it was run for and that is a finding, not a
verdict to accept.

Repairing what you find:

- **Duplicate names** → `POST /dev-tools/retire-contexts {project_id, context_ids:[…]}` naming the
  **husk** — the row whose file list is now wrong. Read both rows first and keep the one with the
  correct files. **Do NOT use `/dev-tools/dedupe-contexts` here**: it keeps the *oldest* row by
  `created_at` regardless of content, which in this exact case would have deleted the correct copy
  and left the husk.
- **A null `group`** → from a build after 2026-08-29 this should not happen: the ingest seeds its
  name→id map from the database and mints a group rather than writing NULL. If it does happen, the
  scan output says which context and why (`[Warn] Context 'x' names group 'y', which could not be
  created`), and that line is the finding — report it. A row written BEFORE the fix stays null until
  its context is re-emitted by a scan, and those are UI-only: the user assigns them in Dev Tools →
  Context Ledger. An auto-minted group has no `domain` until somebody sets one, and the Ledger is
  where that happens too.
- **Stale paths / unmapped files** → another scan, or the drift log below.
- After any repair through the bridge, `POST /dev-tools/export-context-map` — the mutation routes
  change the database and leave `context-map.json` untouched, and a stale file is read as truth by
  the next agent.

### If the bridge does not answer

The app is closed. **Do not edit `context-map.json`, and do not write your own.** Append one line to
`.vault/map-drift.md` (create it if absent) and say so in your final message:

```
2026-08-11 · added app/_phases/motion/{ShotCard,useShotState}.tsx · needs: subtree scan app/_phases/motion
```

The next session that finds the bridge alive drains that file — it runs the scans listed, then clears
the lines it satisfied.

### Two things a session must NOT do

- **Never call `/dev-tools/consolidate-contexts`.** It merges small contexts up into Personas' 10–30
  files-per-context band — which would fuse exactly the per-step contexts this project wants. It is
  the user's call, never a cleanup step.
- **Never create or pin a context.** Creating, renaming and pinning are UI-only actions (Dev Tools →
  Context Ledger); the bridge deliberately exposes no route for them. If the map needs a context that
  a scan will not produce, say so and let the user create and pin it — a **pinned** context survives
  full rescans verbatim and is never absorbed by consolidation, at the cost that new files are never
  auto-added to it.

### Why the map is coarse today, and how it becomes per-step

The target shape is **one context per studio step** — script, frames, motion, score, cut — because
each is going to be developed separately and will grow its own components, state and fixtures.
Today's map does not look like that: all five surfaces sit in one `production-phases` context.

That is not an oversight, it is the scan's granularity rule: **one context per 10–30 files, never
under 8**, aligned to the deepest directory whose file count fits. We tested it — a subtree scan of
`app/_phases/script` (1 file) read the rule, refused to create a standalone context, and folded the
file back into the sibling. **A subtree scan of a directory with fewer than ~8 source files will not
give you a context; it will merge, and it may duplicate.** Don't spend a scan on one.

So the split is earned, not requested:

1. **Each step already owns a directory** (`app/_phases/script|frames|motion|score|cut/`). Keep every
   new file for a step inside its step directory — step-local components, hooks, state, and fixtures
   that only that step reads. Shared fixtures stay in `app/_studio/` (`scenes.ts` and `score.ts` are
   read by two steps each, which is exactly why they are shared).
2. **When a step directory reaches ~8+ files**, run a subtree scan of just that directory. It will
   emit a context of its own, and the taxonomy shifts from "one production-phases" to per-step
   without anyone rewriting anything.
3. **If you need the per-step split before the files exist** — because the map is steering planning
   work now — that is a Context Ledger job, not a scan: create the contexts in the app and **pin**
   them. Pinned contexts survive full rescans verbatim and are never absorbed by consolidation. The
   cost is that new files are never auto-added to a pinned context, so unpin them once the
   directories have grown enough for a scan to own them properly.

The rule underneath all three: **the directory shape decides the map.** The layout you write today is
the taxonomy you get tomorrow.

## The app does not explain itself

**Delete every sentence whose subject is the app. Keep every sentence whose subject is the work.**

That is the law, and the test is literally the grammatical subject:

- *The app.* "This tab shows…", "read across a row to see…", "a cue is a span of film…", "kept so
  that a script written under the old rule can be spotted…", "drag any layer to move it". The screen
  narrating its own mechanism, its own layout, or how to operate it. **It goes.**
- *The work.* A beat, a claim, a cut reason, a gate detail and its quote, a price, a vendor, a model,
  a run id, a constraint, a real error message. **It stays, verbatim** — and shortening it is the
  same defect in the other direction.

This is not a style preference, it was a measurement. On 2026-09-08 seven routes carried 410 rendered
prose strings across 100 component files; five independent route audits found ~170 places where a
component was accompanied by a sentence explaining what the component already showed, and all five
then proposed the SAME handful of replacement shapes. The pass that removed them is finished. What
follows is how it stays that way.

### The vocabulary comes first, always

`components/ui/signal/` — read its `README.md` before writing a new surface; it carries the law in
full, each component, and the call site each was derived from. `Hint · Tally · PipRow · StackBar ·
BandTrack · Ghost · UpstreamBreak · Keycaps · StaleBadge · Provenance · TabRail`.

The reason prose kept being the answer is that **prose was the only primitive available**. If a
sentence is the only way you can say something, that is evidence the vocabulary is missing a shape —
add the shape, in `signal/`, once, and say so. Do not hand-roll a second spelling of a chip that
already exists; that trades one inconsistency for another.

### A container with a slot for a paragraph will be handed a paragraph

Every time, by everyone. `Deck`'s `sub` and four hand-rolled tab bars' `blurb` fields were not places
narration happened to land — they were the reason it was written. **Do not add an explanatory slot to
a shared component.** A tab that needs a paragraph is a tab with a bad label; the state that
paragraph described belongs on the tab as a `<Tally>`.

### The twelve-word rule, and what it is not

`<Hint>` is the most useful and most dangerous thing in the vocabulary: it will hold anything. Moving
a sixty-word explanation behind a glyph **hides** narration, it does not delete it.

> If a disclosure runs past roughly twelve words it is usually still the app narrating itself.
> Delete it instead.

Twelve is an aspiration, not a wall, and the difference was measured: a hard 12 fails seven real
disclosures in this tree and only one of them is narration. A disclosure naming three real things
costs fourteen words. `npm run check:narration` therefore holds a *budget* that may only fall, plus a
25-word hard cap that fails outright — past that it is a paragraph wearing a glyph.

### The gate, and the two things it cannot do

`npm run check:narration` (in `npm run verify`) guards the two mechanical channels narration escapes
through: the count of long native `title=` attributes (a ratchet — relocation is the failure mode of
a deletion pass), and `<Hint>` length. `pipeline/check-narration.mjs` states its own limits in its
header, and they are worth repeating here:

1. **It cannot tell whether a sentence's subject is the app or the work.** That judgement is the
   whole law and no regex will hold it. The gate guards the escape hatches; the law is enforced by
   reading the diff.
2. **It cannot see a hole.** The one defect that survived the entire refactor was a `<Ghost>` drawn
   at ~0.12 effective alpha — invisible on this app's ink ground. Every gate was green, the narration
   census read 100% converted, and the accessibility channel was correct throughout (`Ghost` renders
   an `sr-only` label), so only the *sighted* reading was broken. Nothing that can be asserted caught
   it. **Photographing the screen did.**

So when you delete a paragraph, look at what is left:

```bash
NEXT_PUBLIC_DEV_AUTH=1 NEXT_DIST_DIR=.next-cx npx next dev -p 3007      # then, per screen:
CX_BASE=http://localhost:3007 node pipeline/cx-capture.mjs <screen-id> out.png --width 1920
```

`pipeline/cx-capture.mjs` resolves the 17 named screens (`landing`, `projects`, `wizard-*`,
`studio-*`, `library-*`, `playground`, `foundry`). **Open the PNG.** A deleted paragraph must leave a
shape, not a gap.

### Accessibility is not narration

`aria-label`, `sr-only` and a `<Hint>`'s body are the non-visual channel. When a sentence becomes a
glyph, a colour or a position, the glyph still needs an accessible name — a shape only a sighted
mouse user can read is a regression, not a fix. Never delete a11y text to lower a word count.

### Three standing exemptions

- **Code comments keep their literary register.** This law is about rendered text only. When you
  delete UI prose that recorded a real reason, move the reason into a comment rather than losing it.
- **Real errors explain themselves in full.** `components/ui/NotificationBell.tsx`'s storage-failure
  copy ("This browser's storage is full… a reload would lose it") is the product working, not the app
  narrating. So is a destructive confirm's statement of consequence.
- **`<Keycaps>`.** A keymap is a table, not prose: every row is a key and a verb, and its length is a
  function of how many keys the surface binds.

## Git policy (harness-enforced)

**Commit on the current branch; never push.** The owner pushes after reading the log. Do not push, force-push, or open a pull request unless this session's prompt asks for it. This line exists because the harness's own default for an unattended session is to push and open a draft PR when the file says nothing (measured 2026-09-08: without such a line the agent pushed; with it the agent stopped at the commit). The gate bypass is denied to agents at the permission layer (`.claude/settings.json` `permissions.deny`: `--no-verify`, force-push, `GRAVITONE_SKIP_GATE=1`) - do not work around it; if a gate is red, fix the tree.
