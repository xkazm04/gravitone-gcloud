## Keeping the context map true — REQUIRED when you add, move or delete files

Everything above the markers and everything below them is hand-written and safe to edit. The block
between the markers, and `context-map.json` itself, are **generated by the Personas app** from its own
database. There is no import path: **a hand edit to `context-map.json` is erased by the next scan**,
and until then it is a lie that three skills (`/perfect`, `/explorer`, `/uat`) read as truth. So never
edit it — refresh it instead, in the session that caused the drift.

This repo is young and about to grow a lot: each studio step (script · frames · motion · score · cut)
becomes its own body of code. A map that lags behind that growth is worse than no map, because the
contexts stop matching where the work actually is.

### When to refresh

Refresh if your session **added, moved, renamed or deleted** any file under `app/` or `components/`,
or created a new directory there. A pure edit inside existing files needs nothing — the map tracks
file ownership, not content. Do it at the end of the session, once, not per commit.

### How to refresh (the app must be running)

The Personas app exposes a loopback bridge. The port is not fixed: it is the first free port at or
above **17400**, so probe upward rather than hard-coding one.

```bash
# 1. Find the bridge (probe 17400..17410; stop at the first that answers)
for p in $(seq 17400 17410); do
  curl -s -m 1 "http://127.0.0.1:$p/dev-tools/projects" >/dev/null && { PORT=$p; break; }
done
# 2. This repo's project id (stable; confirm against /dev-tools/projects if unsure)
PID=91d8170c-2be4-45ac-b509-256bfa7726f1

# 3a. Files changed inside existing areas → DELTA scan (cheap; updates only what moved)
curl -s -X POST "http://127.0.0.1:$PORT/dev-tools/scan-codebase" \
  -H 'content-type: application/json' \
  -d "{\"project_id\":\"$PID\",\"root_path\":\"C:/Users/mkdol/dolla/gravitone-gcloud\",\"delta_mode\":true}"

# 3b. A NEW step directory that deserves its own context → SUBTREE scan (scoped, safe:
#     a subtree scan never clears the rest of the map)
curl -s -X POST "http://127.0.0.1:$PORT/dev-tools/scan-codebase" \
  -H 'content-type: application/json' \
  -d "{\"project_id\":\"$PID\",\"root_path\":\"C:/Users/mkdol/dolla/gravitone-gcloud\",\"subtree\":\"app/_phases/motion\"}"

# 4. Poll until status is done/failed — it streams progress lines
curl -s "http://127.0.0.1:$PORT/dev-tools/scan-status/<scan_id>"

# 5. The scan re-exports context-map.json + this CLAUDE.md block itself. Only if you need a
#    re-export without a scan:
curl -s -X POST "http://127.0.0.1:$PORT/dev-tools/export-context-map" \
  -H 'content-type: application/json' -d "{\"project_id\":\"$PID\"}"
```

A scan costs a real LLM run, so it is a once-per-session act, not a reflex. Report in your final
message which mode you ran and what the map gained or lost.

If you lose a `scan_id` (a `curl` inside a `while read` loop eats stdin and swallows its output),
recover it from `GET /dev-tools/scans/{project_id}` — never relaunch blindly, that scans the same
scope twice at full token cost.

### ALWAYS verify the map after a scan — a scan can corrupt it

Measured on 2026-08-11, running a subtree scan over a 1-file directory: the model correctly refused
to create an under-band context and re-emitted the sibling instead — but it emitted a *create*
(`context_map_context`) rather than an *update*, so the row was **inserted a second time**, with a
null group, while the self-heal pruned the moved paths out of the original. The map briefly held two
`production-phases` contexts, one of them ungrouped, with five files double-mapped. Every scan mode
can do this. So after any scan:

```bash
python -c "
import json,glob,os
d=json.load(open('context-map.json',encoding='utf-8'))
names=[c['name'] for c in d['contexts']]
print('duplicates:', {n for n in names if names.count(n)>1})
print('ungrouped :', [c['name'] for c in d['contexts'] if not c['group']])
print('stale     :', [(c['name'],p) for c in d['contexts'] for p in c['file_paths'] if not os.path.exists(p)])
mapped={p for c in d['contexts'] for p in c['file_paths']}
src={p.replace(chr(92),'/') for pat in ('app/**/*.ts*','app/**/*.css','components/**/*.ts*') for p in glob.glob(pat,recursive=True)}
print('unmapped  :', sorted(src-mapped))"
```

Repairing what you find:

- **Duplicate names** → `POST /dev-tools/retire-contexts {project_id, context_ids:[…]}` naming the
  **husk** — the row whose file list is now wrong. Read both rows first and keep the one with the
  correct files. **Do NOT use `/dev-tools/dedupe-contexts` here**: it keeps the *oldest* row by
  `created_at` regardless of content, which in this exact case would have deleted the correct copy
  and left the husk.
- **A null `group`** → UI-only. Say so; the user assigns it in Dev Tools → Context Ledger.
- **Stale paths / unmapped files** → another scan, or the drift log below.
- After any repair through the bridge, `POST /dev-tools/export-context-map` — the mutation routes
  change the database and leave `context-map.json` untouched, and a stale file is read as truth by
  the next agent.

### If the bridge does not answer

The app is closed. **Do not edit `context-map.json`, and do not write your own.** Append one line to
`.vault/map-drift.md` (create it if absent) and say so in your final message:

```
2026-08-11 · added app/_phases/motion/{ShotCard,useShotState}.tsx · needs: subtree scan app/_phases/motion
```

The next session that finds the bridge alive drains that file — it runs the scans listed, then clears
the lines it satisfied.

### Two things a session must NOT do

- **Never call `/dev-tools/consolidate-contexts`.** It merges small contexts up into Personas' 10–30
  files-per-context band — which would fuse exactly the per-step contexts this project wants. It is
  the user's call, never a cleanup step.
- **Never create or pin a context.** Creating, renaming and pinning are UI-only actions (Dev Tools →
  Context Ledger); the bridge deliberately exposes no route for them. If the map needs a context that
  a scan will not produce, say so and let the user create and pin it — a **pinned** context survives
  full rescans verbatim and is never absorbed by consolidation, at the cost that new files are never
  auto-added to it.

### Why the map is coarse today, and how it becomes per-step

The target shape is **one context per studio step** — script, frames, motion, score, cut — because
each is going to be developed separately and will grow its own components, state and fixtures.
Today's map does not look like that: all five surfaces sit in one `production-phases` context.

That is not an oversight, it is the scan's granularity rule: **one context per 10–30 files, never
under 8**, aligned to the deepest directory whose file count fits. We tested it — a subtree scan of
`app/_phases/script` (1 file) read the rule, refused to create a standalone context, and folded the
file back into the sibling. **A subtree scan of a directory with fewer than ~8 source files will not
give you a context; it will merge, and it may duplicate.** Don't spend a scan on one.

So the split is earned, not requested:

1. **Each step already owns a directory** (`app/_phases/script|frames|motion|score|cut/`). Keep every
   new file for a step inside its step directory — step-local components, hooks, state, and fixtures
   that only that step reads. Shared fixtures stay in `app/_studio/` (`scenes.ts` and `score.ts` are
   read by two steps each, which is exactly why they are shared).
2. **When a step directory reaches ~8+ files**, run a subtree scan of just that directory. It will
   emit a context of its own, and the taxonomy shifts from "one production-phases" to per-step
   without anyone rewriting anything.
3. **If you need the per-step split before the files exist** — because the map is steering planning
   work now — that is a Context Ledger job, not a scan: create the contexts in the app and **pin**
   them. Pinned contexts survive full rescans verbatim and are never absorbed by consolidation. The
   cost is that new files are never auto-added to a pinned context, so unpin them once the
   directories have grown enough for a scan to own them properly.

The rule underneath all three: **the directory shape decides the map.** The layout you write today is
the taxonomy you get tomorrow.
